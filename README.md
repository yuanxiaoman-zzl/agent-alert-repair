# 让长任务出错时，主动来找你

在 vibe coding 的工作方式下，任务安排好就去忙别的，很常见。但一个哈希对不上、一次 OOM、一个接续脚本的小问题，就可能卡住整个队列。为了放心，只能不停查看进度。

**不希望十个小时后回来，才发现任务在第十分钟就停了。** 这个小工具就是为此做的：发现异常先发邮件，再按授权调用 agent 尝试修复，最后告诉你改了什么、有没有恢复。平时由普通脚本巡检，不需要模型一直盯着。

**报警要能到你手机上，而不是只在电脑旁响一下。** 人去忙别的事情时，电脑响铃、终端报错或进度窗变红，都可能被错过。手机通常随身携带，邮件到达后弹出横幅或锁屏提醒，更容易及时被看到，让你在离开电脑后也能知道任务出了问题。

所以这里把**报警邮件送到手机、确认手机真的会提醒**作为部署验收的一部分。需要开启手机邮箱客户端的新邮件通知，并实测横幅／锁屏提醒；静音、勿扰、省电或网络状态仍可能影响提醒，不能只凭程序显示“邮件已发送”就认为人已经收到。

这是我的部署经验和脱敏参考代码。**仓库不是一键安装包**：邮箱绑定、任务状态采集和定时运行，需要让你的 agent 按实际环境补齐。

## 它怎么工作

**后台巡检 → 确认异常 → 邮件报警 → 按授权调用agent修复 → 邮件报告 → 独立复查**

1. **平时不用模型盯着**：普通后台脚本检查任务状态，区分正常等待与异常停滞。
2. **发现问题，邮件提醒到手机**：保存现场，把报警发到你手机能接收通知的邮箱。首封报警被邮件服务器接受后，才进入修复流程；手机通知是否正常，要在部署时实际确认。
3. **agent只做一次有界尝试**：在你允许的范围内诊断、修复；遇到无法安全处理的问题就保留现场，不反复重启或重算。
4. **把结果发回来，再核实**：第二封邮件说明改了什么、验证了什么、还有什么未解决；后台继续独立复查任务是否恢复，不能只凭agent一句“修好了”。

你可以先只开报警，确认稳定后再授权自动修复。正常巡检不调用模型，只有确认异常且获得授权时才拉起agent。

## 我是怎么部署的

我手动准备 QQ 邮箱、开启第三方服务并生成授权码；后面的邮箱绑定、报警脚本和修复 agent 接入，都是交给 agent 做的。你也可以按这个顺序来。

### 1. 准备 QQ 邮箱授权码

登录 [QQ 邮箱网页版](https://mail.qq.com/)，依次进入：

**设置 → 账号与安全 → 安全设置 → POP3/IMAP/SMTP/Exchange/CardDAV/CalDAV 服务**

开启带 SMTP 的服务（例如 POP3/SMTP 或 IMAP/SMTP），按页面完成安全验证，再生成授权码。旧版页面可能在“设置 → 账户”中；以实际界面为准。这个路径也可参考[客户端厂商的设置说明](https://consumer.huawei.com/cn/support/content/zh-cn00696857/)。

我的部署使用这些发信参数：

| 配置 | 填什么 |
|---|---|
| SMTP服务器 | `smtp.qq.com` |
| 端口与加密 | `465`，SSL/TLS |
| 登录用户名 | 完整QQ邮箱地址 |
| 登录密码 | 刚生成的**授权码**，不是QQ登录密码 |
| 收件人 | 你要接收报警的邮箱，也可以发给自己 |

发报警用的是 SMTP，不需要脚本读取你的收件箱。授权码不要贴进聊天、提交到仓库或写进命令行；让 agent 提供本机隐藏输入方式，保存到仓库外的私有文件，Linux／WSL下权限设为600。通知程序读取即可，不要让修复模型拿到邮件凭证。

### 2. 把部署交给 agent

准备好项目路径、任务如何启动、在哪里看进度，以及接收报警的邮箱，然后把下面这段交给 agent，替换方括号即可：

```text
请参考 https://github.com/yuanxiaoman-zzl/agent-alert-repair，
为我的长任务部署外挂报警和有界修复。先读README，适配时查docs/TECHNICAL_DETAILS.md。

环境：[操作系统、任务所在主机]
项目与状态入口：[项目路径、启动方式、已有状态文件或日志]
通知邮箱：[发件邮箱、收件邮箱；不在这里填授权码]
修复使用的agent：[本机已安装并登录的CLI、模型与推理强度]
允许修复：[明确可改的文件或操作；尚不确定时先仅报警]

请分阶段完成：
1. 先接通QQ邮箱SMTP。提供本机隐藏输入授权码的方式，凭证放在仓库外，
   不回显、不进日志、不交给修复模型。发送一封明确标为测试的邮件，
   我确认手机实际收到后，再继续接入任务。
2. 复用现有状态入口做只读巡检，补齐此仓库未提供的SMTP、采集和定时适配。
   区分任务失败、正常慢任务、人工暂停与采集失败，避免频繁误报。
3. 故障确认后先邮件报警，再在本任务明确授权内调用一次修复agent，
   报告修改、验证和剩余问题；随后由独立巡检复查，不能只信模型说已恢复。
4. 先用隔离测试目录模拟故障，验证报警、agent启动、修复报告和去重；
   测试通过再挂接本次任务，不影响已有计算。

同事件最多一次自动修复，全局串行，并设超时和每日调用上限。
不要重放整批入口、忽略哈希校验、改科学参数或恢复人工暂停。
OOM先核查资源与退出证据，不能盲目重启。
不能安全修复就保留现场并报告，修复中断后也不要自动重跑。
请留下查看状态、暂停报警和完整停用的方法；以后新任务不要默认挂载。
```

这里的重点是让 agent **适配你的任务**，不用自己手写整套监控。仓库提供事件去重、先通知再修复、调用预算和超时等参考组件；现有任务怎么判断“正常”和“卡住”，仍要按实际运行方式确认。

### 3. 这样验收，才算部署成功

- **先看手机**：实际收到测试邮件，按需要打开通知、确认锁屏也能提醒。程序显示“SMTP接受”还不够。
- **再看演练**：只破坏隔离目录中的测试心跳等合成对象，确认先报警、后启动agent、再收到修改报告；同一故障不会反复拉起模型。
- **最后接任务**：核验真实任务有持续进度，正常等待不误报，人工暂停不会被恢复。知道如何查看和停用外挂后，再放心离开。

未授权修复时，可以先只用邮件报警。后面根据遇到的问题，逐项补充可修复范围。

## 几点实际经验

**不要指望所有故障都能自动修好。** 哈希不匹配可能确实是文件被改了，OOM也可能需要重新分配资源。这个工具首先要做到及时通知、保留现场；能在授权内安全修复时再尝试。

主机休眠、关机或完全断网，本机脚本也无法及时发信。需要覆盖这些情况，要从另一台独立主机观察。另外，修复模型需要已有可用的登录与额度，定时启动时也要核验其运行环境。

运行日志、邮件与修复报告可能带私人信息，别直接上传到公开Issue。这里发布的都是脱敏代码和合成样例，没有原邮箱、服务器配置或实际任务记录。

想看实现或验证代码：[详细设计](docs/TECHNICAL_DETAILS.md) · [发布审核](docs/PUBLISH_REVIEW.md)。隔离测试不会发邮件或调用模型：
